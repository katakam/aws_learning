Kafka: partitions, consumer groups, lag, DLQ, outbox

The ideas a director must be able to explain simply

NOT: A faster message queue where ordering and delivery are automatic.
IS: A partitioned, replicated log: ordering per partition, consumers track offsets, and you design for duplicates and failures.

Why this mattersWhy does this matter? The role mentions Kafka for event driven integration. Interviewers want to hear that you understand ordering, duplicates, lag and failure handling, not just that Kafka is a message queue. Explain these four ideas simply, and you will sound like someone who has run it in production.
  1. Kafka in one picture: a topic split into partitions, read by a consumer group.🛺 Railway: line = topic, track = partition, porters = consumers, offset = how far each porter has unloaded.
  2. The producer chooses the partition from the key (here the tenant). Same key, same partition, same order.
  3. Events are appended to partitions. Order is guaranteed only inside a partition.
  4. Each partition is read by exactly one consumer in the group. More consumers than partitions sit idle.
  5. If consumers fall behind, lag grows. Check slow handlers, hot partitions, downstream timeouts.
  6. Delivery is at-least-once in practice, so handlers must be idempotent (dedupe by event id).
  7. Poison messages go to a dead-letter topic after bounded retries, with an alert and a replay tool.
  8. To avoid "DB saved, Kafka failed", write the event to an outbox table in the same transaction and let a relay publish it.
