NVIDIA GPU Operator: what runs on a GPU node

Bring-up order and what each operand does

NOT: A pile of scripts you run by hand on every node after every kernel upgrade.
IS: A Kubernetes operator that deploys, orders and health-gates the whole GPU software stack declaratively.

Why this mattersWhat are we trying to do here? A GPU node needs many things installed in the right order: driver, toolkit, plugin, labels, monitoring. Doing that by hand on hundreds of nodes, after every kernel upgrade, is a nightmare. The GPU Operator automates it. In an interview this shows you think about operating at scale, not just installing once.
  1. One Helm install, one ClusterPolicy. The Operator then runs everything a GPU node needs.🛺 Society maintenance office: one contract covers electrician, plumber and guard for every flat.
  2. NFD detects the NVIDIA PCI device and labels the node, so GPU operands only run where GPUs exist.
  3. Driver (skip it if the AMI already ships one, e.g. EKS accelerated AMI).
  4. Container toolkit configures containerd and CDI so containers can be given device files.
  5. Device plugin registers nvidia.com/gpu with kubelet. The validator gates it until driver and toolkit pass.
  6. GFD publishes labels such as nvidia.com/gpu.product for scheduling by model.
  7. DCGM Exporter exposes utilisation, memory, power and XID errors to Prometheus.
  8. MIG Manager (optional) applies MIG layouts when you label the node. Gotcha: editing the time-slicing ConfigMap needs a device-plugin restart.
