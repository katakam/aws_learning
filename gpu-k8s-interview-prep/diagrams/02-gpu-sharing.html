Sharing a GPU: exclusive, time-slicing, MIG, MPS

Pick the right wall between tenants

NOT: Fractional GPUs do not exist in the scheduler. nvidia.com/gpu: 0.5 is invalid.
IS: Sharing is a node-level feature (time-slicing, MPS, MIG) that changes what the device plugin advertises, or DRA claims that describe it.

Why this mattersWhy does this matter? Exclusive is the default mode, and it is simple and safe, but expensive. A GPU costs a lot of money, and if one job uses only a fifth of it, the rest sits idle. Interviewers love asking how you would raise GPU utilisation, and this is the starting point of that answer. First understand what is wasted, then look at the sharing options.
  1. Default mode: one GPU = one Pod. Whole bungalow, one family.
  2. Pod A gets the full GPU. Safe, full isolation, best for training and big models.
  3. Pods B and C stay Pending (Insufficient nvidia.com/gpu): extended resources are integers and never overcommitted.
  4. If A only uses ~20 %, the rest is wasted. That is why sharing exists.
Why this mattersWhy does this matter? Time-slicing is the cheapest way to share a GPU, so teams reach for it first. But it has a hidden danger: there is no wall between the jobs. In an interview, the right answer is not 'it shares the GPU', the right answer is: good for dev and notebooks, never for tenants who do not trust each other.
  1. Time-slicing: the GPU is shared by turns.🛺 One auto-rickshaw, passengers take turns.
  2. Config says replicas: 4, so the plugin advertises 4 "GPUs" for 1 physical device.
  3. Three Pods each get a replica. Replicas are scheduling slots, not extra capacity.
  4. The GPU runs Pod A for a slice…
  5. …then Pod B…
  6. …then Pod C. Context-switch overhead each time.
  7. No memory or fault isolation. One greedy Pod can hurt the others. Use for dev, notebooks, light inference, never for untrusted tenants.
Why this mattersWhy does this matter? When you run a platform for external customers, you must promise that one customer cannot slow down or crash another. MIG gives hardware walls inside one GPU, so it is the answer for strong isolation. Be ready to also explain the cost: the slices are fixed, so some capacity can be stranded.
  1. MIG cuts one GPU into hardware-isolated instances (A100/A30/H100/H200/B200 families).🛺 Separate flats in one building: own walls, own meter.
  2. Ask for a layout by labelling the node. The GPU must be idle.
  3. MIG Manager carves the GPU. Each slice gets dedicated memory, cache and SMs.
  4. The device plugin advertises per-profile resources such as nvidia.com/mig-1g.10gb (mixed strategy).
  5. Pods request a slice and land on it. Predictable latency, strong isolation.
  6. A Pod that overruns its slice OOMs only inside its own slice. Neighbours are untouched. Downside: static geometry, stranded capacity.
Why this mattersWhy does this matter? MPS is the middle path: jobs really run at the same time, so throughput is better than time-slicing, but the isolation is weaker than MIG. Knowing all four options, and when to use each, is what separates a platform owner from someone who only used GPUs.
  1. MPS lets several processes share the GPU concurrently.🛺 One shared kitchen: several cooks work at once.
  2. The MPS control daemon starts a server that owns the GPU context.
  3. Client processes connect to the server instead of the GPU directly.
  4. Kernels from different processes overlap in time: better throughput for many small kernels than time-slicing.
  5. Limits: active-thread percentage and pinned-memory caps per client. Isolation is weaker than MIG (a fault can affect other clients).
