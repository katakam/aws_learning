Spring Boot: startup and request lifecycle

From java -jar to ready, and from HTTP request to GPU and back

NOT: Spring Boot is not magic. Every default is a conditional bean you can override.
IS: Spring + starters + auto-configuration + embedded server + Actuator, with a predictable filter → servlet → controller path.

Why this mattersWhat are we trying to do? Follow one request through a Spring Boot service, step by step, so you can explain where security, validation, limits and timeouts belong. At the end the call goes to a GPU model server, which is slow and expensive, so the service must protect it. Interviewers use this to check whether you can review a design, not just write code.
  1. Request lifecycle in Spring MVC, with a GPU backend at the end.🛺 Courier path: gate → security desk → reception → right department → warehouse → back.
  2. Client sends POST /v1/chat/completions.
  3. Tomcat parses HTTP and assigns a thread (a virtual thread when spring.threads.virtual.enabled=true).
  4. Filter chain (servlet level): Spring Security validates the JWT, logging and tracing add context.
  5. DispatcherServlet finds the handler; interceptors run preHandle.
  6. Controller: Jackson binds JSON to the argument; validation runs.
  7. Bulkhead takes a slot. No slot within 200 ms → 429 + Retry-After instead of piling onto the GPU.
  8. RestClient calls the model server with explicit connect/read timeouts.
  9. Response flows back: message converter writes JSON, the slot is released in finally, latency is recorded.
Why this mattersWhy does this matter? Many Spring Boot problems come from not knowing what the framework does at startup. Knowing the sequence, and that your own bean always wins over the default, lets you debug surprises quickly and review other people's code with confidence.
  1. What happens between java -jar and "ready".🛺 Maggi masala packet: the framework adds the default spices unless you brought your own.
  2. SpringApplication.run() begins.
  3. Environment is built: application.yml, env vars, command line, profiles.
  4. An ApplicationContext is created (servlet or reactive, decided by the classpath).
  5. Component scan finds your beans; auto-configuration classes listed in AutoConfiguration.imports are considered.
  6. Each auto-config is guarded by conditions. Your own bean wins because of @ConditionalOnMissingBean.
  7. Singletons are created, dependencies injected, @PostConstruct runs.
  8. Embedded Tomcat starts and binds the port(s).
  9. Runners execute, ApplicationReadyEvent fires, readiness turns ACCEPTING_TRAFFIC.
