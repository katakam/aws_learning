From Pod YAML to GPU

Device plugin → kubelet → scheduler → runtime → driver

NOT: Kubernetes does not understand GPUs. The scheduler just counts an opaque integer.
IS: A device plugin advertises nvidia.com/gpu; the toolkit exposes the chosen device; the host driver does the work.

Why this mattersWhat are we trying to understand? When you write one line in a YAML file asking for a GPU, what really happens behind the scenes? Kubernetes does not know what a GPU is. It only counts a number. So several small components cooperate: one announces the GPUs, one picks the machine, and one hands over the key. This is the most common question on any GPU platform interview. If you can walk through it calmly, it shows you understand the whole stack, not just one tool.
  1. A Pod asks for a GPU by count. Follow it from YAML to silicon.🛺 Booking "1 taxi", not "taxi number 7".
  2. Node boot: the device plugin registers nvidia.com/gpu with kubelet and streams 4 healthy GPUs (ListAndWatch). kubelet reports capacity to the API server.🛺 Dispatcher tells the control room: "4 taxis at this depot".
  3. You submit a Pod with limits: nvidia.com/gpu: 1.🛺 Passenger asks for one taxi.
  4. Scheduler filter: NodeResourcesFit needs allocatable GPU ≥ 1. Taints, nodeSelector and quota are checked too.🛺 Control room looks for a depot with a free taxi.
  5. Bind: the Pod is assigned to this node and kubelet receives it.
  6. kubelet calls Allocate(). The plugin picks GPU 2 and returns its UUID (or a CDI device name).🛺 Dispatcher hands over the key of one specific taxi.
  7. kubelet asks containerd to start the container. The NVIDIA toolkit mounts /dev/nvidia2, /dev/nvidiactl and the host driver libraries.
  8. Container runs. nvidia-smi shows only GPU 2; CUDA calls go to the host driver. Driver on host, CUDA toolkit in the image.🛺 Passenger sees only their taxi, not the whole depot.
